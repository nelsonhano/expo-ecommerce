# Review, main, 2026-11-07

**Reviewed by**: Sonnet 5.5 (author model not stated)
**Scope**: 35 files (30 tracked, 5 untracked; lock file skipped), uncommitted on main
**Verdict**: Approve with nits

## Summary
The change moves checkout to authorize, reserve stock in a MongoDB transaction, then capture, with one reconcile function that every webhook event goes through. I traced the reconcile table against spec 0001 (AC-1 to AC-16) and found it faithful: stock moves only through conditional updates, order insert and stock take share one transaction, release is guarded on `authorized`, and Stripe is never called inside a transaction callback. No blockers or majors. The findings below are minor edge cases around bad metadata, the legacy path, and a few UI and server details. The earlier hardening edits (auth middleware, id validation, cart cleanup, admin guards) are sound.

## Minor
### 🟡 Bad metadata can leave a card authorization hanging, `backend/src/controllers/payment.controller.js:30`
**Problem**: The address check only tests that each field is truthy, so an object or array passes. The webhook later fails on `JSON.parse` or a Mongoose cast error in `baseOrder` / `Order.create` (`backend/src/services/checkout.service.js:98`, `:139`). That is not a stock shortage and not a Stripe error, so reconcile throws, the webhook returns 500, and Stripe retries for days. No order is saved and nothing cancels the PaymentIntent, so the hold stays until it expires. A very long address can also push the `shippingAddress` metadata value past Stripe's 500 character limit, which turns into a generic 500 from create-intent (only `orderItems` has the size guard). The same retry loop would hit any PaymentIntent in a shared Stripe account that has no `orderItems` metadata.
**Why it matters**: Only the caller hurts themselves with bad input, and the real mobile app sends strings, so impact is low. But the design has no way out for a permanently unbuildable order.
**Suggested fix**: Require each address field to be a string with a length cap, and apply the 500 character check to the address value too. In reconcile, treat a metadata parse failure as permanent: cancel the PaymentIntent and log it, instead of retrying forever.

### 🟡 Legacy path ignores the "short" result, `backend/src/services/checkout.service.js:274`
**Problem**: `fulfilLegacyPayment` takes only `items` from `buildOrderItems` and drops the `short` flag. If a product was deleted, or an id is invalid, the customer was already charged in full, yet an order is saved without that line (or with no lines at all, if every id is invalid).
**Why it matters**: A silent partial order for a paid cart. It only affects intents created before the deploy, for about a week.
**Suggested fix**: If `short` is set, use the same refund route the stock failure uses, and log it.

### 🟡 Cancel reason can be wrong after a retried capture failure, `backend/src/services/checkout.service.js:210`
**Problem**: In `capture`, the PaymentIntent is cancelled and then `release(..., "capture_failed")` runs. If the process dies or `release` throws between those two steps, the retry sees a `canceled` intent with an `authorized` order and releases with `authorization_expired`. The spec's reconcile table says that case should use `capture_failed` when a capture failure caused the cancel.
**Why it matters**: Stock is still restored once and the customer is still not charged, so only the reason label (and the mobile message) is off.
**Suggested fix**: Accept it and note it in the spec, or release first and then cancel at Stripe. Release is guarded, so the order of the two steps is safe either way.

### 🟡 Body parse errors now come back as 500, `backend/src/server.js:68`
**Problem**: The new error handler only maps upload errors. Anything else, including malformed JSON or an oversized body from `express.json()`, which carry `err.status` 400 or 413, now returns 500 "Internal server error" and logs as unhandled. Express's default handler used to return the right status.
**Why it matters**: Client mistakes look like server faults and add noise to logs and alerts.
**Suggested fix**: Honour `err.status` or `err.statusCode` when it is a 4xx.

### 🟡 Outcome alert may not show on iOS, `mobile/app/(tabs)/cart.tsx:183`
**Problem**: `setConfirming(false)` closes the `Modal` and `Alert.alert` is called a few lines later in the same tick. On iOS, React Native can drop an alert shown while a modal is still dismissing. I could not run the app, so this is a known risk and not a confirmed failure.
**Why it matters**: The customer could see no "Order placed" or "not charged" message at all (AC-7). The data is still in My Orders.
**Suggested fix**: Show the alert from the Modal's `onDismiss`, or after a short delay, and check on a real iOS device.

### 🟡 Admin category list drops "Accessories", `admin/src/pages/ProductsPage.jsx:8`
**Problem**: The hard coded list no longer has "Accessories". Editing an existing product with that category shows a blank required select, so the admin must change the category to save. The comment says the list matches mobile and the seed data; I did not check that against existing database rows.
**Why it matters**: Surprising edit failures for old products.
**Suggested fix**: Check live product categories, or keep the product's current category in the options when editing.

### 🟡 Unrelated pinned SDK changes in a payments change, `mobile/package.json:20`
**Problem**: `@stripe/stripe-react-native` goes from `^0.57.0` to an exact `0.50.3`, Sentry from `^7.7.0` to `~7.2.0`, and `expo-auth-session` is added. These look like Expo SDK 54 version alignment, but a downgrade of the payment SDK sits inside the PaymentSheet change.
**Why it matters**: Checkout behaviour depends on the SDK. The change is easy to miss in review.
**Suggested fix**: Confirm it was intended, ideally as its own commit, and test PaymentSheet on a device with the pinned version.

## Strengths
- The reconcile function is idempotent and driven by the live PaymentIntent, not the event type, so event order and duplicate delivery are handled by construction. Transaction callbacks stay free of Stripe calls, and the duplicate key path re-reads instead of cancelling.
- Money safety is careful: sold out records the cancelled order before cancelling at Stripe, release is guarded on `authorized` so stock returns at most once, and the pre validate hook enforces `cancelReason` only when cancelled.
- Good hardening around it: `by-payment` returns 404 for non owners and unknown ids, the old unauthenticated style `createOrder` route is gone, `protectRoute` returns JSON 401 instead of redirecting, and the backfill script refuses to run if duplicate payment ids exist.
